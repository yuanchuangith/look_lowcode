# 多轮低代码复核：意图与关系检索优化评估

日期：2026-09-06。范围：当前仓库与本线程对话；离线合成探针，不查询业务数据库，不调整已安装插件、不发布平台动作。

## 结论

值得优化，但应先修复证据定位与沟通契约，而不是先增加向量库、全库扫描或更多提示词。
这段对话主要暴露的是动作调用关系、字段传递关系和本次业务约束的理解问题，并非可信数据库关系阈值不足。
建议首轮做报告分类、会话约束记录、字段引用检索、局部调用身份四项；生成代码定位和响应预算随后处理。
本次仅给评估、复现脚本和验收建议，没有修改运行实现、Skill 内容或测试断言。

## 1. 现有能力与保留项

- Skill 已有会话锚点、用户规则优先、源码升级门禁、草稿/发布语义、三态控制流等约束；不是从零缺失。
- CanvasInspector 已提取条件 AST、字段映射、调用参数、相邻节点与控制结构，适合增量扩展。
- 现有 Schema 可信关系和用户否决策略应保留；更多候选不等于更多已确认关系。
- 调用链、字段流与数据库外键是不同证据：前两者的静态关联不自动升级为数据验证关系。
- 前后端源码工具已有响应预算相关实现和测试经验，可评估复用到画布输出，而非另建重复机制。

## 2. 优先级与源码位置

### P1-A：报告分类，正常结果不要叫“问题1”

位置：`skills/gxp-lowcode-debug/SKILL.md:139`、`skills/gxp-lowcode-debug/references/report-contract.md:20`。

两处均强制诊断第一行使用“问题1”。本线程在已通过的检查前也使用了该前缀，用户随后问“问题1有什么问题吗”。这有直接的契约诱因，不只是检索算法问题。

建议用互斥分类：已确认缺陷、条件性风险、可选加固、已通过、待验证。无确认缺陷时直接说明“本次静态复核未发现新增确定缺陷”，再说明验收边界。
只给真实缺陷稳定的缺陷编号；风险、建议和已通过清单使用独立标签，不把章节序号当问题编号。
“用户说已解决”记录为待复核；重新读取修改位置后再更新为静态已修复；实际运行成功单独记录。

验收：用户追问“第1项有问题吗”“2、3解决了”时，明确指向之前的对应项，不把正常项误认成 Bug，也不声称已复核未读取的修改。

### P1-B：把会话锚点扩为小型业务约束表

位置：`skills/gxp-lowcode-debug/SKILL.md:36`、`mcp/gxp_core/diagnostics.py:557`。

现有三行规则偏向下拉“允许选择什么”，对生成、去重、推送和错误处理不够贴合。diagnose_codex_input 当前接受单段 text 和 at_time，没有显式会话约束参数；短句接续依赖模型上下文。

建议 Skill 先维护小型结构，按需再为工具增加显式、可选 context 参数：

| 内容 | 本次对话的实例 | 生命周期 |
|---|---|---|
| 当前目标 | 初始培训的关联文件去重 | 用户切换任务时重新定界 |
| 当前动作/分组 | 已确认的动作 code、RefId、group_key | 复用身份；复核时刷新设计版本 |
| 字段含义 | 用户纠正后 member_id 要使用；nodeData.id 的业务含义 | 保存纠正来源，旧说法标为被替代 |
| 本次排除项 | class_hour 不采用；周期排序忽略 | 用户重新纳入前不再报相关建议 |
| 业务不变量 | 主技能历史去重和文件本次内容去重分开 | 区分本次规则与跨项目默认规则 |
| 无匹配/空值策略 | 无文件匹配正常带出；某必填标识缺失应报错 | 明确到具体字段/动作，不泛化 |
| 已选实现 | 字符串传参、子动作分割 | 非必要不反复切换成全局数组或JSON方案 |
| 已知缺陷 | 稳定ID、状态、上次证据版本 | 版本变化后重新验证，非自动关闭 |

这是会话级信息，不把本项目的 member_id、flow_id 或排除项硬编码进通用插件，也不写入共享关系否决库。
优先从已明确对话建立约束，短句身份唯一时直接复核；只有实际影响方案的歧义才问一个针对性问题。

验收：连续纠正、排除项、用户自选方案、短句“再看看”、编号指代和项目切换均有回放案例。

### P1-C：字段检索从“字段名命中”扩展到“读写引用命中”

位置：`mcp/gxp_core/canvas.py:1652`、`mcp/gxp_core/service.py:281`。

focus_fields 目前覆盖映射/过滤/调用参数，以及变量定义名称等，但遗漏条件操作数、variable_value、assignment_value 和循环来源里的引用。
服务在仅传 focus_fields 时又据此过滤节点，所以“条件里用了字段但返回0节点”会被误读为没有使用。

离线探针：条件 trainingType 与变量值 detail["file_ver_id"] 都存在；focus_count 为0，普通 terms 搜索各为1。

建议保留 focus_fields 兼容行为，补充结构化引用类别或显式 reference 检索模式：定义、读取、写入、条件、循环、调用传参、返回值。
每个命中返回 source_path、原表达式、分组、节点、角色及匹配方式。零结果应区分“覆盖范围内无匹配”与“当前分析未覆盖此表达式”。
先识别已有 AST/结构中的简单引用；复杂 C# 保持候选，不执行表达式、不用子串相似冒充确定字段流。

验收：前述两项命中；相近字段名不误命中；字符串字面量与真实引用分级；已知条件范围保留。

### P1-D：保留局部调用目标身份，再做跨分组字段传递

位置：`mcp/gxp_core/canvas.py:399`、`mcp/gxp_core/canvas.py:1071`。

node_facts 读取 actionName 的 code/id/name/label，却未保留本线程 CallAction 使用的 actionName.value 分组 key。
图构造随后使用 code/id/name 作为调用目标。合成两个同名、不同 group_key 的局部调用时，返回了两个完全相同的 name，code/id 都为空。

建议增加明确的调用种类、target_group_key、target_ref_id 和解析状态。局部调用在当前 action+design 内按 group_key 解析；公共动作按实际编号/RefId 解析。
图节点身份至少包含动作身份、设计身份和分组 key。变量节点也按分组作用域区分，避免不同分组的 detail 被当成同一个变量。
第二步再连实参到形参、循环项到查询结果、返回值到调用方；沿当前入口和父分支追踪，不能靠相似分组名选择一条路径。

验收：同名分组、未调用旧分组、两个调用入口漏传一个、同名局部变量、动态目标未解析、递归限深。

## 3. 后续值得做的工具优化

### P2-A：生成 C# 先定位方法范围

位置：`mcp/gxp_core/service.py:395`、`mcp/gxp_core/canvas.py:1758`。

指定 node_key 后，当前仍提取通用字段词并搜索整个 action 的 C#。探针把真实目标放在第26行，前25行放在其他方法；该节点的候选只返回第1至10行，目标未进入列表。
结果已标 exact_source_map=false，这是正确的保留项；问题是候选召回和排序，不是工具声称自己拥有精确 source map。

建议先解析当前分组方法及变量/赋值片段，再在方法内找候选；无法证明对应方法时保留全局候选并明确范围未解析。控制原始方法行号与画布行号，按设计哈希失效缓存。
验证表达式错误前读取最终生成代码，区分 Convert.ToString 的转换、局部集合、共享全局JSON值与前端JS数组。

### P2-B：精确分组优先、输出按字节预算

位置：`mcp/gxp_core/canvas.py:1321`、`mcp/gxp_core/service.py:342`。

group 当前使用子串匹配；探针 group="main" 同时返回 main 和 main-copy。建议 key 精确匹配优先，其次唯一标题，再回退模糊候选并提示歧义。
一个50,000字符表达式的单节点响应达102,186字节，nodes_truncated=false、too_broad_for_params=false；节点数量门禁没有限制重复的 facts/params 内容。

建议新增字节预算与显式输出级别，优先位置/简要事实，再按节点取参数；省略字段必须标明并提供精确续读方式。
重要的否定条件、版本、控制流状态不允许被静默删掉。既有序列化预算机制可以评估复用，但不能只截字符串而丢语义。

### P2-C：知识主题可发现，而非靠猜名字

位置：`mcp/gxp_core/cpm_snapshot.py:301`。

本线程尝试 reference/global-variables 返回 KNOWLEDGE_NOT_ALLOWED。白名单应保留，但可提供小型主题目录、参数示例或合法别名映射，优先返回变量元件与语言边界的具体主题。
示例代码应附执行端、参数类型、元件类型、输入位置和空值规则，并在给画布方案前检验声明/赋值/表达式填入位置。

## 4. 场景证据，不靠“字段少了”直接判错

建议对去重、过滤和关联关系统一补充：对象身份、记录版本、当前流程/计划、当前人员、层级、状态、生成先后、实际调用入口。
这些是待确认的维度，不是要求所有查询无条件追加全部字段。

例如已有 flow_id 或 position_training_id 限制时，必须证明同一限定范围还能出现冲突记录，才把“范围串入”升级为确定缺陷。
用户明确某字段缺失应报错时，尊重 fail-fast 规则，不强行套用“为空正常跳过”。主技能已培训但文件待培训的链路应分别追踪创建端、过滤端和调用入口。

## 5. 测试与证据

离线复现脚本：`docs/conversation-accuracy-review-probes.py`。使用仓库 mcp 目录作为 PYTHONPATH，使用已有 Look Python 环境执行。FixtureRepository 完全替代真实仓库访问。

| 探针 | 当前观察 | 性质 |
|---|---|---|
| 条件引用 | focus 0，文本1 | 检索覆盖不足 |
| 变量值引用 | focus 0，文本1 | 检索覆盖不足 |

| 无上下文追问 | not_found，建议resolve_action | API不携带会话上下文；不是LLM理解能力的独立测量 |

这说明现有测试未约束这些新增验收目标；不表示全套系统已运行验证，也不表示上述改动已经实现。

后续多轮回放至少包括：member_id纠正、class_hour排除、周期排序排除、保留已有全局排序、主技能与文件分开去重、同流程范围反例、节点id含义澄清、用户选字符串方案、前后端变量类型、已解决与已复核、正常项编号、发布后行号变动。
行为验收应看最终结论、证据绑定、额外调用数及建议是否执行在正确分组；仅检查Skill包含几个关键词不足以衡量命中意思。
目前没有修改前后同一模型的多轮A/B数据，因此不报告准确率提升百分比。

## 6. 实施顺序与不做项

1. 小补丁：报告分类、约束表/排除项/稳定问题ID、用户选择方案优先。用会话回放验收，而非只叠提示词。
2. 代码补丁：条件与变量引用、局部调用value身份、精确分组、上述探针对应的回归测试。
3. 再做方法内C#定位、字节预算、限深跨调用字段流与知识目录。保留 unresolved，不要求一次构建全平台图。
4. 经过代表性会话回放和测试后，再由用户决定是否通过仓库安装器更新插件；本轮未安装、部署或发布。

暂不建议：降低可信关系阈值、将本次业务字段写成通用规则、把所有会话存入永久共享记忆、引入向量库掩盖精确身份丢失、扩大无边界源码/业务库扫描。
