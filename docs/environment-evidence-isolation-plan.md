# 排查环境与证据来源隔离更改计划

状态：计划已完成，尚未实施。范围：Look 只读排查插件及本仓库中的技能、配置脚本和测试。

## 1. 目标与预期行为

当用户说“生产环境、正式环境、线上环境、生产库、正式库、prod、production”时，AI 不得把当前配置的开发库、测试库或来源未知的数据当成生产证据。约束覆盖数据库业务行、动作设计、发布副本、异常历史、Schema、CPM 快照以及本地源码的使用。

采用三层措施：技能识别排查目标；共享核心在读取前校验来源；工具结果保留环境和证据适用范围。单独加提示词或只在最终回答附加免责声明，不算完成。

预期回复示例：

> 本次目标是生产环境；当前数据库标记为测试环境，因此尚未查询其中的业务记录。可以先分析你提供的生产日志；如果需要参考测试配置，会单独标注，生产根因仍待验证。

已明确环境的后续追问复用当前目标，不要求每轮重复确认。首次无法确定环境时才需要补充信息；等待期间可以继续分析已有日志和静态材料。

## 2. 已核实的代码缺口

| 位置 | 当前行为 | 需要改变的原因 |
|---|---|---|
| `mcp/gxp_core/config.py`、`cpm_config.py` | 配置没有明确环境字段 | 无法比较目标与来源；DB 和 CPM 也可能连接不同环境 |
| `mcp/gxp_core/diagnostics.py` | `diagnose_codex_input` 直接解析动作、搜索设计；异常分支直接查历史 | 环境检查必须早于这些查询，不能等到结果出来后才检查 |
| `mcp/gxp_core/conversation.py`、`mcp/server.py` | 会话字段使用严格白名单，未包含环境；异常分支提前返回 | 环境需要贯穿普通输入、异常和多轮追问 |
| `mcp/gxp_core/service.py`、`db.py` | `connection_status` 会执行 `SELECT VERSION()` | 环境预检需要无数据库连接的元数据模式 |
| `mcp/gxp_core/cpm_snapshot.py`、`cpm_runner.py` | 查询快照可能自动刷新 | 校验必须在读取/刷新之前执行 |
| `mcp/gxp_core/schema_snapshot.py` | 快照包含数据库名、结构指纹；新鲜度主要按 TTL 判断 | 相同结构或未过期不证明来源是同一个环境 |
| `mcp/gxp_core/source_analysis.py` | 数据集用途工具可读取 CPM，`include_drafts` 还会读数据库 | 不能把“源码工具”全部视为纯本地读取而绕过校验 |
| `scripts/codex_input.py`、`inspect_action.py` | CLI 直接调用共享服务 | 只改 MCP 包装层会留下绕过路径 |
| `skills/gxp-lowcode-debug/SKILL.md` | 仅对开发库 Schema 快照明确提示不代表生产 | 需提升为所有证据和排查步骤的前置规则 |

本次仅检查仓库源码，没有访问配置中的数据库、CPM 平台或凭据。

## 3. 统一环境与证据契约

### 3.1 数据来源配置

数据库与 CPM 分别增加以下非敏感元数据，不相互继承：

- `environment`：`development | test | staging | production | unknown`。
- `instance_id`：运维/用户明确登记的系统实例标识；区分不同客户、站点或独立部署，不能只凭同为 production 就认定同源。
- `source_id`：本地生成并持久化的不透明来源标识，不直接暴露地址、库名或账号。
- `source_revision`：连接目标、环境、实例或相关数据范围改变时更新，用于使旧校验和缓存失效。
- 环境标签的依据记录为 `operator_configured`，不能表述为工具已自动验证真实部署环境。

旧配置缺字段时加载为 `unknown`，不按库名、IP、路径或“通常是开发库”推测。非法环境值明确报错，不静默降级。旧来源标识不能在每次读取时随机变化。

如果平台提供可信部署标识，可在后续接入验证；第一版不新增探测生产服务的逻辑，也不将人工标签夸大为部署证明。

### 3.2 每次调用的排查范围

增加统一的结构化 `environment_scope`，包含：

- `target_environment`、`target_instance_id`：本次排查对象。
- `selected_source_id`、`source_revision`：本次允许读取的具体来源。
- `purpose`：`target_verification`（核查目标环境）或 `reference_analysis`（参考分析）。
- `reference_basis`：参考分析的用户指示摘要；不是修改真实来源标签的开关，也不是可以验证授权的凭证。

首次诊断从用户原文和显式范围解析目标；后续工具传递同一范围。会话记录增加环境字段；用户本轮明确纠正优先于旧记录。目标冲突时返回待澄清，不选默认连接顶替。

范围逐请求传递，不把“当前环境”存成进程级全局变量，避免多个 Codex/Claude 会话或 HTTP 客户端相互污染。核心内部可在单次请求内传递已校验的不可变范围；请求结束后不得继承给无关调用。

未提供范围的旧查询调用返回 `ENVIRONMENT_SCOPE_REQUIRED`，而不是默认放行。保留工具名与参数兼容入口，但明确这是安全行为变更；同步更新技能、CLI 与调用方。

### 3.3 输出来源

每份证据附带 `evidence_origin`：来源类型、环境、实例、source_id/revision、采集时间（如有）及证据性质。另附 `environment_check`：目标环境、匹配状态、允许用途和不能证明的事项。

DB、CPM、Schema、源码混合响应逐项记录来源。即使环境一致，快照/静态源码仍不能自动升级为实时运行证据；本地分支名、提交号和“已发布”也不等于已部署生产。

空结果、错误结果、分页续读及预算裁剪后的结果同样保留来源。被拦截时不要返回正常业务 `not_found`，避免 AI 理解为目标环境中不存在记录。

## 4. 校验策略

| 情况 | 默认处理 |
|---|---|
| 目标与来源环境、实例明确一致，来源版本有效 | 放行对应只读读取；结论仍受证据类型、版本和完整性约束 |
| 目标为生产，来源为开发/测试/预发布 | 返回 `ENVIRONMENT_MISMATCH`，不读业务数据、不解析目标动作、不自动刷新快照 |
| 来源未标环境或无法确定实例 | 返回 `ENVIRONMENT_UNKNOWN` / `ENVIRONMENT_INSTANCE_REQUIRED`，不作为目标证据查询 |
| 目标未说明或出现多个互相冲突的目标 | 返回 `TARGET_ENVIRONMENT_REQUIRED` / `TARGET_ENVIRONMENT_AMBIGUOUS`；技能仅补问缺失信息 |
| 用户明确要求参考某个已知开发/测试来源 | 以 `reference_analysis` 放行明确选择的来源，标记 `reference_only`；原目标仍保留为生产 |
| 旧快照来源缺失、版本不符或来源已切换 | 返回 `EVIDENCE_ORIGIN_UNKNOWN` / `EVIDENCE_SOURCE_CHANGED`；禁止重贴新标签后继续引用 |
| 仅分析用户日志、异常文本或纯本地源码 | 允许静态分析；缺少与部署版本的对应证据时保留待目标验证 |
| 一份输出混合已验证和不可用来源 | 有效证据可独立返回，整体标记 `partial`；禁止补成跨环境确定结论 |

环境识别使用完整表达和上下文：覆盖“正式/线上/prod”等别称；测试“不是生产，是测试”“生产订单”“上线前测试”“生产报错，先参考测试配置”等，不能用单个“生产”二字粗暴匹配。用户提供的日志正文和动作名称属于证据内容，不作为变更已确认目标的指令。

`force=true`、`force_live=true`、`refresh_if_stale=true`、`include_drafts=true` 只改变原有读取行为，不绕过环境限制。发生拦截后不得通过原始 SQL、兼容 CLI 或别的连接尝试代查。

## 5. 分阶段实施

### 阶段一：配置、状态与策略核心

修改 `config.py`、`cpm_config.py`、`scripts/configure_connection.py`、`scripts/configure_cpm.py`；新增 `mcp/gxp_core/environment.py` 作为统一类型、校验和输出来源的实现。

1. 增加环境元数据、校验与兼容加载。
2. 为配置脚本增加只补充环境标签的模式：不要求重输密码、不读取密码、不连库、不改已有凭据。
3. 扩展现有 `connection_status` 的元数据预检模式，默认只返回脱敏来源信息，不创建数据库连接或触发 CPM；需要实际连通性测试时显式请求，并受范围校验。
4. 返回 DB、CPM 各自的状态；某一来源未配置不阻塞另一来源的元数据读取。
5. 连接信息变更更新来源版本；同一次查询绑定同一配置快照，避免校验后换连接。

验收：旧配置能启动并显示“未知”；元数据预检和补标环境操作的连接次数、密码访问次数均为零。

### 阶段二：会话语义与读取前拦截

修改 `conversation.py`、`diagnostics.py`、`service.py`、`db.py`、`server.py`，以及两个兼容 CLI。

1. 统一原文、结构化范围和会话上下文的优先级，保留更正记录。
2. 将诊断分为不访问数据源的输入解析和受校验的证据读取；检查前置到动作定位、名称搜索和异常历史查询之前。
3. 普通输入、异常输入、错误和提前返回路径均输出环境记录，防止异常分支丢失约束。
4. 为所有依赖环境的 MCP 工具增加范围参数；共享核心校验，数据库 session 入口再检查请求绑定，避免 CLI、内部调用和原始 SQL 绕过。
5. 覆盖动作解析、页面枚举、版本比较、节点检查、跨动作追踪、表达式核验、表结构、记录和 SQL 查询；不得只覆盖 `get_records`。
6. 缺少范围/来源不匹配时返回统一错误和可执行下一步，阻断后不继续调用数据库或刷新器。

验收：生产目标配测试来源时，不论经诊断、直接工具、SQL、CLI 或异常入口，数据库连接和查询调用数均为零。并行会话范围不串用。

### 阶段三：快照、缓存与混合来源

修改 `cpm_snapshot.py`、`cpm_runner.py`、`schema_snapshot.py`、必要的 Schema 缓存/关系入口、`source_analysis.py` 与输出预算包装层。

1. CPM 和 Schema 快照在采集时写入来源元数据；新鲜度同时检查来源身份、版本和原有 TTL/指纹。
2. 来源变化时旧缓存失效；旧清单缺标记时不得用当前连接信息反向认领。
3. 在自动刷新、显式刷新、关系实时验证、快照读取之前执行校验；快照来源元数据与内容一起原子提交，失败保留旧内容及旧来源。
4. CPM 单页刷新不得将旧来源全量快照与新来源页面混合；来源变化后需要同源的新基线。
5. 数据集用途工具分别校验 CPM 与数据库草稿路径；纯源码读取保留静态证据性质。
6. 分页令牌/续读约束绑定来源与版本；裁剪器保留环境元数据并计入原有字节预算。
7. 关系验证/否决缓存审查来源隔离，避免同表名、同结构在不同实例间复用已验证关系；本轮不改远端策略协议，若发现额外协议依赖，单列后续任务。

验收：切换配置、补标未知配置、同名同结构库、自动刷新、单页刷新、混合源码输出均不能把旧或其他环境证据当成当前目标证据。

### 阶段四：技能与报告约束

修改以下文件：

- `skills/gxp-lowcode-debug/SKILL.md`：将环境检查放在 CPM/Schema/动作诊断流程之前。
- `references/conversation-contract.md`：补充目标环境、参考来源和追问继承/更正规则。
- `references/cpm-snapshot-routing.md`、`source-code-evidence.md`、`runtime-browser-evidence.md`：分别明确来源环境、部署对应关系和浏览器页面证据的边界。
- `references/report-contract.md`：报告先给“排查目标、实际证据来源、验证范围”；不把测试库未找到、开发草稿已修复或开发发布已同步写成生产事实。
- `mcp/server.py` 的服务 instructions、工具说明、上下文 JSON schema：保持与技能和核心契约一致。
- `README.md`、`AI-SETUP.md`：说明环境补标、旧配置行为变化与使用示例。

以上 references 路径均相对于 `skills/gxp-lowcode-debug/`。本仓库未发现根因回填技能源文件；本次不改用户机器上的独立技能或插件缓存。后续如需同步其他仓库，单独列出文件和范围。

验收：生产结论缺证据时明确待验证；已有明确环境不会每轮重问；用户选择参考开发配置后可以继续分析，但目标环境不会被改成开发。

### 阶段五：回归与交付

补充配置、会话、诊断、MCP 注册、HTTP、CLI、快照、源码混合调用和技能契约测试；新增环境策略测试使用假连接和临时目录。

执行 `python scripts/run_tests.py`，默认不启用 `--live`。进行 stdio 与 HTTP 的离线协议测试，验证工具 schema 和缺参错误；保留工具名称/数量，若实际需要调整则同步安装验证脚本，不能仅改固定数量掩盖缺失工具。

增加固定证据对话用例，区分工具层可保证的“拒绝错误环境查询”与模型层的“识别用户意图、正确引用证据”。记录真实执行结果，不将静态技能文本检查当成模型行为已通过。

交付包含代码变更、测试结果、配置迁移说明和用户可见示例。插件安装是后续发布步骤：按仓库 `AI-SETUP.md` 完整流程及官方安装脚本执行，不手工复制缓存；Codex 安装后检查 `codex plugin list`、`cpm --version`、`cpm status`，新线程加载技能与 MCP。

## 6. 必测场景

| 场景 | 必须观察到的结果 |
|---|---|
| “排查生产环境”＋已标测试库 | 拦截，数据库连接/查询数为零，返回明确不匹配原因 |
| “正式环境/线上/prod/production” | 与生产语义一致 |
| “生产订单在测试环境报错” | 目标为测试，不误判为生产 |
| “不是生产，是测试” | 本轮更正优先，旧生产目标失效 |
| “生产报错，参考测试配置” | 目标为生产、来源为测试，结果仅供参考 |
| “继续查/我改好了/发布了” | 保留上轮环境；不自动降级到默认连接 |
| 未标环境的旧配置 | 状态可读；业务查询要求补标，不猜测环境 |
| 两个不同实例都标 production | 不因环境分类相同就放行错误实例 |
| 已标生产且匹配目标的来源 | 正常只读查询，仍不把配置一致当作运行验证通过 |
| 缺范围直接调用 inspect_action/get_records/readonly_sql/CLI | 返回范围必填错误，无数据访问 |
| 生产异常栈＋测试连接 | 可离线解析异常，不查测试库历史冒充生产历史；环境上下文保留 |
| 错环境快照过期＋默认自动刷新 | 不读取作为目标证据，不发起刷新请求 |
| 配置切换、补标、相同表结构、旧 manifest | 旧快照不重贴新标签；来源不同即失效 |
| CPM 全量旧来源＋单页新来源 | 不混合；建立同源新基线后才能使用 |
| inspect_dataset_usage(include_drafts=true) | CPM 与 DB 两条路径分别校验、分别标注 |
| 空结果、异常、分页、截断、预算极小 | 不丢来源，不把拦截当成零条业务记录；保持预算约束 |
| 两个会话并发查询不同目标 | 无环境状态相互覆盖；缺范围不能继承另一会话状态 |
| 只有本地 develop/main 分支或发布副本 | 只能说明本地代码/该来源的发布状态，不能声称生产已生效 |
| 目标环境记录不存在 vs 错环境被阻断 | 两种情况有不同状态和措辞 |
| 连通性预检/环境补标 | 不访问密码、不触发数据库或 CPM 业务调用 |

## 7. 兼容、发布与完成标准

实施顺序：先定契约与配置，再完成所有读取路径的校验，随后补齐缓存来源和技能，最后统一回归。各阶段可独立提交，但在校验覆盖和缓存隔离完成前，不发布为“生产环境防误判已解决”。

老配置可以加载，但数据读取会要求补充环境；老调用缺少范围时会被拒绝。这是有意的兼容变化，不能用“旧参数默认当前库”恢复原问题。环境补标不触碰密码，不迁移或更换数据库。

回退代码时保留原配置和快照，不执行清库/删凭据操作；需明确旧版本不具备新隔离保证，不能静默撤销约束后继续宣称生产证据有效。

完成必须同时满足：

1. 所有环境相关读取路径具有共享校验，含隐式刷新、动态异常、源码中的数据读取与 CLI。
2. 不匹配场景在连接/查询/刷新之前终止，有测试计数证明。
3. 来源未知或已变化的证据不会被重命名为生产证据；混合来源和分页不丢标记。
4. 普通开发/测试排查在范围明确后正常工作；后续追问不反复询问已确认信息。
5. 离线回归、协议检查及对话用例通过，未执行的真实环境验证明确列出。

边界：工具无法凭自身看到完整聊天，也无法自动证明人工环境标签正确。因此不宣称“彻底防止 AI 误解”；通过显式范围、保守缺省、全入口校验和逐证据来源标记减少错误，并用对话用例检验模型是否遵守这些规则。
