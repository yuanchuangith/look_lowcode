## Repair acceptance 2026-09-05
- Correctness requires current per-layer source identity, complete candidate-group validation, and a policy revision not predating restoration of the target or a competing candidate. A successful individual match does not establish uniqueness.
- Installed stdio verification uncovered a Windows inherited-input Git stall absent in direct unit calls. DEVNULL stdin fixes the observed stall; ten-second Git timeouts provide structured degradation. Two new tests cover this boundary.
- Final evidence: 148 tests (145 pass, three live skips), 35 local/16 remote tools, lazy index-v2 migration, golden source calls, 17 known comment requests removed, and no business-repository modifications.
- Controlled paired medians: +10.47% build and −32.14% hot query. Concurrent installation contaminated an intermediate run; the baseline outlier is retained and disclosed.
- Final report distinguishes static/fixture verification from unexecuted live DB/page validation and other-machine rollout. See docs/optimization-repair-results.md and docs/optimization-repair-benchmark.json.

- Existing `describe_table` returns only `DESCRIBE` and `SHOW INDEX`; it omits table/column comments and cross-table relationships.
- Existing read-only session enforces `START TRANSACTION READ ONLY`, a 10-second maximum execution time, and a 500-row result cap.
- Existing CPM refresh manager provides cross-platform file locks, temporary work directories, status files, and atomic directory replacement suitable for reuse.
- Local stdio currently registers 21 tools (16 shared database tools plus 5 local CPM tools); HTTP registers only the 16 shared tools.
- Remote HTTP service is a Starlette/FastMCP application and currently has no policy persistence or authentication.
- Python requirements have no HTTP client dependency; standard-library `urllib` and `sqlite3` can implement the policy client/server without adding a package.
- Database is MySQL-compatible through PyMySQL. Schema metadata should come from `information_schema` and must be paginated below the session result cap.
- Remote policy can live beside the existing MCP ASGI app while keeping database-dependent Schema tools local-only.
- A stable per-database `policy_scope_id` plus SHA-256 over normalized endpoints lets the remote service enforce shared rejections without receiving table or column names.
- Strict verified relationships can be represented as a binary state rather than a probabilistic score; ambiguous or under-populated candidates stay outside the trusted graph.
- The deployed systemd service uses `ProtectSystem=strict`; `StateDirectory=gxp-lowcode-readonly` plus an explicit `GXP_RELATION_POLICY_DB` path is required for writable remote policy persistence.
- Policy HTTPS deployments may use a reverse-proxy Host, so the HTTP service accepts explicit additional hosts through `GXP_LOWCODE_HTTP_ALLOWED_HOSTS` while retaining the fixed defaults.
- Full regression after the latest acceptance tests passes 96 tests (3 opt-in live tests skipped); compileall and `git diff --check` also pass.
- Static review found two acceptance gaps to close: restoring a rejected relation currently exposes the old verified snapshot without revalidation, and the validation executor context can wait beyond the refresh deadline for running futures.
- User simplified the remote policy contract: persistence is now a small atomically replaced JSON file and all policy endpoints are authentication-free. The built-in public endpoint/scope lets a newly installed Skill synchronize without moving a token.
- Production endpoint `https://43-135-137-212.sslip.io:8892` is live through Nginx TLS. Policy health reports JSON storage, `gxp-development` is revision 0 with no rejections, and the remote MCP registry remains 16 tools with no local Schema tools.
- The real development database contains 915 tables and 15,640 columns. Bulk metadata paging completes in about 8-14 seconds; indexed candidate discovery replaces the original table Cartesian scan.
- The successful first snapshot evaluated all 977 conservative candidates in about 68 seconds: 28 data-verified relations, 878 insufficient-data candidates, 69 orphan/unmatched candidates, and 2 read timeouts. Timeout candidates stay out of the graph and are prioritized on the next refresh.
- Source implementation will share one resolver between the compatibility search script and structured tools. The resolver must expose checked candidates and Git metadata without reading or persisting source bodies.
- Real frontend anchors confirm `TestPaper` has separate designer and `preview/web` trees plus `api.ts`/`utils.ts`; `GxpSmartTables` consumes `dynamicFilter` into `filterInfo.Filters` and `conditionFilter` into `conditions`, providing concrete filter-contract anchors.
- The real metadata-only source index builds in about 3.1 seconds and contains 2,591 frontend files, 139 components, 967 frontend route occurrences, 543 backend files, 593 ASP.NET endpoints, 362 DTOs and 7,572 brace-bounded backend call edges.
- Real `/api/datasets/search` resolves to `DataSetController.Search → DataCenterQueryDto → DataSetServices.QueryDataCenter`; `/api/datasets/save` preserves three frontend `dataSave` callers and resolves to `DataSetController.DataSave → DataSaveDto → DataSetServices.BatchSaveData`.

## Source-evidence audit (2026-09-05)

- The active `source-code-evidence.md` still hard-codes the obsolete roots `G:\hoyi\updateComponents\gxp2.components` and `G:\hoyi\updateWeb\gxp2.web`; the supplied repositories are now under `F:\cpm\...`, so the documented/script defaults must be checked before any lookup result can be trusted.
- Current source escalation is intentionally gated and only four MCP responses may provide `source_hints`: `diagnose_codex_input`, `inspect_action`, `inspect_component_filters`, and `trace_dynamic_exception`.
- The documented source search is file-oriented fixed-string `rg`: up to 8 exact terms, 4 same-file pairs, 20 files, and context for the top 5. It ranks co-occurrence but does not itself resolve symbols, routes, DTO contracts, call graphs, or component registration/binding chains.
- The Skill correctly separates static frontend/backend source evidence from browser runtime evidence and prohibits ordinary table/field names or `CallAction` alone from triggering repository scans. Any new tooling should preserve this precision gate and explicit ambiguity handling.
- Both supplied repositories are present, clean Git checkouts on `develop`; neither contains an additional `AGENTS.md`. The backend snapshot examined has about 2,141 non-build/non-cache files (859 C# files across Web/Services/IServices/Model plus plugin assets), while the frontend has about 3,771 files (roughly 1,529 TSX and 1,442 TS files).
- Backend code has a highly regular layered shape: `GxP2.Web/Controllers`, `GxP2.IServices`, `GxP2.Services`, and `GxP2.Model/Dto`; observed totals include roughly 83 controllers, 148 services, and 178 DTO-named files. Attribute routes combine controller-level `[Route(...)]` with method-level `[Http* (...)]`, including `[controller]` substitution.
- Frontend code already contains maintained `codemaps/architecture.md`, `frontend.md`, and `data.md`. They document the `designer` versus runtime `preview` split, component auto-discovery via Webpack context, aliases, component groups, service utilities, and schema conventions. These maps are useful routing input but are dated snapshots and should not be treated as direct source evidence without file verification.
- The frontend is large but convention-heavy: `src/core/components/{business,form,engine}`, `src/core/common`, `src/basic`, with most runtime components under `preview/web|wap` and configuration under `designer/schema`. A component-aware resolver can exploit these conventions much more accurately than repository-wide keyword ranking.
- A real execution of the current script confirms the stale-path failure (`repository_not_found` on the old G: root). Passing the two F: roots manually makes it work, so repository-root configuration is a prerequisite rather than a speculative improvement.
- Searching the real frontend for the component type `TestPaper` produces 25 files and truncates at 20. With one equally weighted term, lexical path ordering puts `knowledge/.../试卷.md`, an SVG icon, and generic registries ahead of the runtime `preview/web/index.tsx`; this can hide the implementation context the Skill actually needs.
- The script's `subprocess.run(..., encoding="utf-8")` produces mojibake for Chinese paths/content in this Windows environment when consuming `rg` output, making returned context harder to audit even though direct PowerShell reads are correct.
- Cross-layer experiment: exact `/api/datasets/save` finds three frontend request builders but zero backend files because ASP.NET composes `[Route("api/datasets")]` and `[HttpPost("save")]` across attributes. Searching `DataSetController` finds only the controller and does not follow its injected `IDataSetServices`, implementation, method, or DTO. This is direct evidence that route composition and symbol/call-chain resolution are missing.
- `TestPaper` demonstrates a stable component graph that a structured tool can return: `designer/schema.tsx` declares `Behavior.name`, selector, Resource and defaults; `preview/web/index.tsx` defines runtime props/events and reads/writes `testpaperModel`, `answerModel`, and `qualifiedScoreModel`; `preview/web/api.ts` exposes public methods; central `ComponentEvents.ts`, `ComponentMethods.ts`, and `ComponentProps.ts` register its contract. A generic text search returns these as unrelated files and does not classify their roles.
- `DataFilter.tsx` shows why business semantics need a specialized trace. The low-code element generates assignments to `inbiz(component).conditionFilter` and `.dynamicFilter`; a historical comment states the counter-intuitive mapping: `dynamicWhere` supplies SQL `conditionFilter`, while `staticWhere` supplies JSON-based `dynamicFilter`. Runtime consumers differ by component and apply those functions at request construction time. A `trace_component_filter_contract` tool could surface this designer→generated JS→runtime query chain and the historical inversion explicitly.
- The `/api/datasets/save` chain is structurally recoverable: three frontend `dataSave` builders → `DataSetController.DataSave([FromBody] DataSaveDto)` → `IDataSetServices.BatchSaveData` → `DataSetServices.BatchSaveData` → ZeroEntity insert/update. `DataSaveDto` expects `DataModel`, `PrimaryKey`, and `Data`; one `EditableTable` caller statically passes `{modelKey, changeData}` nested under request `{data}`. This is a high-value contract mismatch candidate, but remains static evidence until the shared request wrapper and runtime payload are verified.
- Current local MCP already has good platform-level scopes (`search_platform_snapshot`, `inspect_page_snapshot`, `get_cpm_knowledge`) and precise database/action tools, but source access is only an external Skill script and is not registered as a structured local MCP tool. Consequently there is no shared typed contract or tool-level enforcement connecting `source_hints` to the allowed layer/terms.
- CPM page inspection exposes `meta`, `tree`, `components`, `bindings`, and `bizflows`, while global snapshot search covers pages, menus, components, models, datasets, dictionaries, events, workflows, interfaces and public actions. New source tools should consume these identities as anchors and return links back to CPM/Look identities, instead of duplicating the platform snapshot.
- The existing search implementation runs a separate `rg` process for every term and repository, then separate context reads. With up to 16 flattened terms across two repositories, it lacks one total deadline and does not exploit a persistent index; this is avoidable latency and produces no symbol-level relationships.
- Backend service wiring is convention-based reflection: controllers inject interfaces such as `IDataSetServices`, implementations declare `DataSetServices : ... IDataSetServices`, and `RegistrationServices.cs` registers discovered interface/implementation pairs. A resolver should index inheritance/interface declarations as well as explicit `AddScoped` calls.
- Frontend component discovery is also machine-readable: `src/core/entry/web.ts` and `wap.ts` use `require.context` patterns for `designer|preview` paths, then `entry/utils/index.ts` selects platform-specific files. This supports exact component role resolution without executing a build.
- Current exclusion rules are too generic for this backend checkout: it contains `.dist`, large `GxP2.Web/wwwroot` vendor/runtime assets, `DBInit` seed JSON, plugin bundles and other non-primary sources not excluded by the script. Layer-specific include roots/extensions are needed so generated/minified/seed content cannot outrank Controllers/Services/DTOs.
- User requires both machine layouts to remain supported. Repository resolution should therefore accept ordered candidates/configuration, including `F:\cpm\...` and the existing `G:\hoyi\...`, not replace one hard-coded root with another. If more than one valid checkout exists, the response must expose the selected path/commit and either apply an explicit priority or return ambiguity.
- A direct probe found a high-impact `source_hints` bug: `IDataSetServices.BatchSaveData` and `DataSetServices.BatchSaveData` produce no backend hint because `SERVICE_SYMBOL` only recognizes suffixes `Service`/`ServiceBase`, not the repository's common plural `Services`. Even a real `GxP2.Services.Data.DataSetServices.BatchSaveData(...)` stack is marked high confidence but yields an empty `exact_terms` list, leaving the search script with no valid query.
- The frontend loader derives the component key from the component directory, combines runtime exports with matching designer schemas, and registers `properCase(key)`. A source index can reproduce this exact mapping statically and return the same identity used at runtime.
- The `TestPaper` runtime demonstrates actual business semantics that a structured component trace should expose: it reads stored JSON from three configured model bindings, creates hidden form fields, updates those fields via `form.setValues`, emits answer/end/save events, and loads multiple dataset roles with distinct relation fields (`primaryKey`, `ref_id`, `data_source_id`, `testpaper_id`, etc.). A single component name is insufficient; the tool must distinguish each configured dataset role and field lifecycle.
- Searching the backend for generic Chinese/English “paper” terms mostly returns watermark/print-paper code, not the training `TestPaper` component. Business-concept lookup must therefore bind display terms to the resolved component type and its configured datasets before expanding to backend symbols; raw Chinese full-text search would create convincing false positives.
- `fetchDataByDataSet` builds a `DataCenterQueryDto`-shaped payload and delegates to the shared `SearchDataCenter` request builder for `/api/datasets/search`; the backend composes the corresponding route and calls `QueryDataCenter`. This confirms that useful business tracing often crosses component-local helper → shared frontend service → controller → service implementation, not just one source file.
- The repositories contain enough regular structure for a high-value index: 115 frontend Behavior/Resource component definitions, about 733 `request.get/post/put/patch/delete` call sites and 957 API-literal occurrences; backend has 83 controllers, 89 controller route attributes, about 600 HTTP method attributes and about 100 convention-wired service implementations.
- Route parsing must implement ASP.NET semantics, not string concatenation only: examples include `api/[controller]`, `api/{controller}`, a leading-slash controller route, method routes with placeholders/optional parameters, and absolute method routes such as `[HttpGet("/api/network/blacklist")]` that override the controller prefix.
- The backend already contains two useful domain-discovery implementations. `FormFieldExtractor` parses page schema into component/model/table-column information, and `DataSetServices.GetDataSetRelatedRef` locates dataset use across forms, current published business actions, public actions and workbenches. The report-generation endpoint itself creates tasks/files, so a readonly Skill tool should reuse the parsing/query ideas rather than call that mutating workflow.
- A structured `inspect_dataset_usage` tool is especially valuable: the current backend reference feature already distinguishes forms, published business actions, public actions and workbenches, while the Skill today can only do generic snapshot text search or manual record queries. The readonly implementation should return exact current identities and preserve draft/published evidence labels.
- Existing source-search tests use tiny synthetic repositories and validate bounds/exclusions/co-occurrence only. They do not cover candidate path selection, two valid checkouts, Chinese Windows output, plural `*Services` symbols, composed/absolute ASP.NET routes, component role classification, DTO recursion, interface→implementation resolution, or generated/external URLs.
- Source-derived tools belong in the local stdio registry only. The remote MCP cannot see either local checkout, and uploading source/index data would violate the same locality principle used for the Schema snapshot. A local index may store paths, symbols, routes, component contracts and edges; source bodies should still be read live in bounded context from the selected checkout.
- Source index freshness should be keyed to repository fingerprints (selected root + commit + dirty-file metadata), not only a time TTL. A clean commit can reuse its index indefinitely; any relevant dirty-file change should invalidate affected entries so line numbers and contracts do not silently go stale.
- Independent review 2026-09-05: isolated probes confirm stale source indexes can emit exact evidence, comments/plain strings become requests, and arrow functions inherit the previous function name. A unique unrelated short method name is followed as a structural backend edge. Schema refresh promotes one passing target despite another target timing out; restoring a rejection on one machine leaves another machine's old verified cache reusable without validation. Control-flow symbolic operators (=, ==, !=, <>) regress to unknown. Git porcelain output is stripped before fixed-column parsing, truncating the first unstaged path and hiding subsequent edits from fingerprints. All probes use temporary files and mocked DB/policy/Git outputs.
- Review measurement checkpoint: real readonly scans reproduce 967 frontend routes, 17 line-comment pseudo-requests, 185 missing function identities and 457 missing methods; backend has 593 endpoints and 7,572 edges. Golden datasets save/search chains resolve with wrapper_unresolved preserved. Single-scan times were 15.365s frontend and 3.989s backend, not a controlled old/new benchmark. Historical Schema 68s/TTL 0.016s measurements are explicitly attributed to earlier progress records, not this review.
- Repair decisions: additive protocol v2 restores per-relation revision tombstones, retains JSON format v1, versions ETags, and invalidates cached ETags after mutations. Candidate completeness now includes truncation and errors. Source index v2 uses NUL porcelain plus content hashes and per-layer guarded reads. Existing source-tool fixture is migrated to typed symbol IDs rather than retaining the unsafe legacy short-name resolver.
